# OmniLLM 概要设计

> 状态：v0.5（2026-10-18）。v0.2 按原则 1、2 重做了网络结构；v0.3 架构评审修正（§11）；v0.4 产品评审修正（§10、§12）；v0.5 改为库优先，以 SDK 融入 NEXA、不另装软件（§2.4、§8）。
> 一句话：**一处接入大模型，所有设备都能用。** OmniLLM 是一个个人工具，不是平台。
> 本文服从 [principles.md](principles.md)。两者冲突时以原则为准。

## 1. 定位与范围

**是什么**：一个 Go 库（SDK），加上用它做成的单文件程序。库可以嵌进别的程序（首先是 NEXA），程序给没有 NEXA 的人单独用。装在“中心节点”（Mac、PC 或服务器）上时，它是**唯一**和大模型打交道的地方，保管所有凭据；其他设备（手机、平板、别的电脑或服务器）配对后，经过中转服务器、以端到端加密的方式请中心节点代为调用模型。

**解决的问题**：

- 每台设备都要配一遍 API Key 或登录一遍，凭据散落各处，丢一台设备就得全部换掉。
- 多台设备、多个 IP 同时用一个账号，容易被提供商判定为账号共享而封号。
- 本地模型（Ollama 等）只能在本机用，手机、平板用不上。

**设计原则**（详见 [principles.md](principles.md)）：

1. **只有中心节点和大模型交互，账号不能被封**。
2. **中心节点和设备之间只经过服务器中转，端到端非对称加密，服务器看不到内容**。
3. 凭据（API Key 和登录会话）不出中心节点。
4. 默认安全。
5. 规则写在代码里。
6. 够用就好：一个主人，多台自己的设备。
7. **以代码（SDK）融入 NEXA，不另外安装软件**：OmniLLM 首先是 Go 库，NEXA 直接引入，当它的大模型和 AI 应用（§2.4、§8）。
8. **不懂技术的人也能 5 分钟用上**：不需要自己的服务器，向导三步走完（§10）。

**谁能用**：有至少一个官方 API Key（OpenAI、Anthropic、Gemini 等），或者在中心节点上装了本地模型（如 Ollama）。**只有网页版订阅（ChatGPT Plus、Claude Pro）、没有 API Key 的人用不了云端模型**：订阅的网页登录不允许第三方程序使用，强行用会封号。这一点在安装说明和向导第一步就说清楚。

**不做（v1）**：多用户或团队计费；把账号分享给别人用；导出或转发网页版订阅的登录态；局域网直连或点对点组网。

## 2. 总体架构

```
                         模型提供商（OpenAI / Anthropic / Gemini …）、本地模型
                                        ▲
                                        │  唯一的上游出口（限流 · 退避 · 熔断）
 ┌──────────────────── 中心节点 omnillm hub（不开放任何对外端口）─────────────────┐
 │  E2E 会话层   Noise IK：校验设备公钥 → 解密请求 / 加密响应                       │
 │  鉴权层       设备公钥白名单 → 可用模型、额度、到期                              │
 │  路由层       统一请求格式 → 选择 Provider → 流式结果                           │
 │  Provider 出口 OpenAI · Anthropic · Gemini · OpenAI 兼容 · Ollama               │
 │  凭据库       API Key 和登录会话，系统钥匙串 / age 加密文件                       │
 │  控制台       仅限本机 127.0.0.1，凭本机登录用户身份：配对、吊销、额度、审计       │
 │  存储         SQLite：设备公钥、额度、审计（默认不存对话内容）                    │
 └───────────────────────────────┬──────────────────────────────────────────────┘
                                 │ 主动外连 wss://（TLS）
                                 ▼   帧内容：端到端密文
                    ┌──────── 中转服务器 omnillm relay ────────┐
                    │  按随机信箱编号转发字节；不落盘、不记内容  │
                    │  看不到：内容、模型、用量、设备名、凭据     │
                    └──────────▲──────────────▲──────────▲──────┘
                               │ 主动外连 wss://           │
                         手机 / 平板        其他电脑        服务器 / 脚本
                        （网页客户端 /    （omnillm connect：  （omnillm connect：
                          原生 App）        本机 OpenAI 接口）    本机 OpenAI 接口）
```

设备和中心节点都只做**主动外连**，彼此之间没有任何直连路径。中心节点不监听对外端口，只开本机管理端口。

### 2.1 组件

| 组件 | 说明 |
|---|---|
| OmniLLM 库（SDK） | 全部能力的实现，嵌入 NEXA 等宿主时直接引入（§2.4） |
| `omnillm hub` | 独立程序的主机模式：库的 `hub` 包外加控制台、CLI |
| `omnillm relay` | 中转服务器，同一个程序的另一种模式；按设计**不可信**，谁部署都一样 |
| `omnillm connect` | 设备端代理：在设备本机开一个 `127.0.0.1` 的 OpenAI 兼容接口，把请求加密后经 relay 发给中心节点。现有 App 和 SDK 把 `base_url` 指向它即可 |
| 网页客户端 | 手机、平板用的聊天页面，从独立的静态地址发布（不由 relay 下发，见 §5.3） |
| 本机控制台 | 中心节点上的网页控制台（`omnillm open` 打开），首次运行向导、配对、设备、额度、用量都在这里；只在本机，靠本机登录用户的身份进入，不另设密码 |
| `omnillm` CLI | 和控制台功能相同的命令行（`pair`、`devices`、`revoke`、`status`、`app`、`backup`），也可在终端里对话 |
| 本机应用接口 | 中心节点和 `omnillm connect` 都只在 `127.0.0.1` 开 OpenAI 兼容接口，给同一台机器上不能嵌入库的第三方程序用；每个程序一枚应用令牌。NEXA 以库嵌入，不走这里 |

### 2.2 部署方式

| | 个人电脑做中心 | 服务器做中心 |
|---|---|---|
| 中心节点 | Mac / PC 上的 `omnillm hub` | VPS 或 NAS 上的 `omnillm hub` |
| 中转服务器 | **默认用项目提供的公共 relay，什么都不用装**；想自己掌握元数据，可以在自己的服务器上跑 `omnillm relay` | 同左；自己部署时可以和中心节点在同一台机器上，但中心节点仍只经 relay 和设备通信 |
| 凭据存放 | 系统钥匙串 | 加密文件，主密钥来自环境变量、systemd credential 或 KMS |
| 上游出口 | 这台电脑的网络 | 这台服务器的网络 |

### 2.3 一次请求的流程

1. 设备上的 App 调用本机 `omnillm connect` 的 `POST /v1/chat/completions`（或在网页客户端里发消息）。
2. 设备用和中心节点之间的 Noise 会话密钥加密请求，填充到固定长度档位，发到 relay 上自己的信箱。
3. relay 把密文原样转给在线的中心节点。它解不开，也不记录。
4. 中心节点解密，用设备公钥确认是哪台设备，检查是否被吊销、能否用这个模型、额度还剩多少。
5. 请求进入 Provider 出口：排队、限并发、限速；取出凭据发给提供商；遇到 429 按要求退避。
6. 结果按块加密、填充，经 relay 流式返回；为了省流量，流式内容每约 100 毫秒合并成一块再发，也顺带减少从节奏推测长度。设备端解密后交给 App。
7. 中心节点累计 token 用量，写一条审计（时间、设备、模型、token 数，不含内容）。

### 2.4 库优先：一套代码，两种用法

```
            ┌──────────────── OmniLLM 库（Go 模块 github.com/wensuper/OmniLLM）────────────────┐
            │  hub      主机：Provider 出口、凭据、设备、额度、审计、配对、工具转接                    │
            │  device   设备：连到主机、调模型、执行宿主登记的工具                                   │
            │  relay    连接服务（单独部署用）                                                     │
            │  宿主接口  SecretStore · Store · Transport · Logger · Locale · UI（确认、通知） · ToolHost │
            └───────────────┬──────────────────────────────────────────┬─────────────────────────┘
                            │ 嵌入                                       │ 包一层
                    NEXA（pgclient）                           omnillm 独立程序
              钥匙串、存储、出站出口、界面都用 NEXA 的        控制台、CLI、connect，用库自带的默认实现
```

**公开接口（草案）**

| 包 | 主要接口 | 说明 |
|---|---|---|
| `hub` | `New(Options) (*Hub, error)`、`Start(ctx)`、`Stop(ctx)` | 宿主决定何时启停；`Stop` 后不留任何 goroutine |
| | `Complete(ctx, Request) (Stream, error)` | 进程内调模型；`Request` 必须标明调用方是人（`Interactive`）还是后台程序（`Background`），后台只能走 API Key 和本地模型 |
| | `Models(ctx) []Model` | 每个模型带 `Locality`（`Local` / `Remote`）、提供方、显示名 |
| | `Pair(ctx, PairOptions) (*Pairing, error)` | 返回二维码内容、配对文字；`Pairing.Code()` 给出 6 位校验码，`Confirm()` / `Cancel()` 由宿主界面调用 |
| | `Devices`、`Revoke`、`Usage`、`SetBudget`、`AddCredential`、`RemoveCredential`、`Backup`、`Restore` | 凭据只能写入、删除和列出（末 4 位），没有读出明文的方法 |
| `device` | `Dial(ctx, Options) (*Device, error)`、`Complete`、`Models` | 主机在别处时，宿主嵌入设备角色 |
| | `RegisterTools(ToolHost)` | 宿主登记可以被远程调用的工具（§8.3） |
| `relay` | `NewServer(Options)` | 只给自己部署连接服务的人用 |

**宿主传入的接口**

| 接口 | NEXA 传入 | 独立程序的默认实现 |
|---|---|---|
| `SecretStore` | NEXA 的钥匙串封装 | 系统钥匙串 / age 加密文件 |
| `Store` | NEXA 数据目录下的一个 SQLite 文件（库自己的表，不碰 NEXA 的表） | 自己数据目录下的 SQLite |
| `Transport`（`http.RoundTripper` 和 WebSocket 拨号） | NEXA 的出站出口 `internal/egress` | 标准库 |
| `Logger` | NEXA 的日志（库已脱敏后再交出） | 标准错误输出 |
| `Locale` | NEXA 当前界面语言 | 系统语言 |
| `UI` | NEXA 的确认框和通知 | 控制台 / 系统通知 |
| `ToolHost` | NEXA 的 MCP 工具分发（§8.3） | 无 |

**错误**：库返回带类型的错误，和本机接口的状态码一一对应：`ErrBusy`（带 `RetryAfter`）、`ErrHubOffline`、`ErrInvalidToken`、`ErrModelNotAllowed`、`ErrUnsupportedFormat`。每个错误带一句给人看的话（按 `Locale`）。

**本机 HTTP 接口和应用令牌**只给不能嵌入库的第三方程序（各种 App、脚本、别的语言写的程序）用；NEXA 不需要它们。

## 3. 密钥、配对与设备管理

### 3.1 密钥

- 中心节点和每台设备各有一对长期的 X25519 公私钥。私钥只在本机：中心节点存进钥匙串；`omnillm connect` 存进设备的系统钥匙串；网页客户端用不可导出的 WebCrypto 密钥存进 IndexedDB。
- 每次会话按 Noise IK 模式握手：设备事先知道中心节点公钥，中心节点检查设备公钥在白名单里；会话密钥由临时密钥协商，具备前向保密。会话按时间和消息数定期重新协商密钥。
- **不做 0-RTT**：Noise IK 的第一条消息可以被录下来重放，所以它只用来握手，不带任何业务数据；握手完成后才收发请求。
- **协议版本**：握手负载里带协议版本和能力列表；协议只增不改，新能力双方都声明了才用，老设备照常能连。
- **换钥**：`omnillm rekey` 生成新的中心节点密钥对，经现有加密会话把新公钥发给每台设备，由旧密钥签名，设备核对后换上；旧私钥疑似泄露时不走这条路，直接全部重新配对。

### 3.2 配对（公钥只能当面交换）

1. 主人在控制台点“添加设备”（或运行 `omnillm pair --name "iPhone"`）。可用模型和额度已经预填（全部已接入的模型、每天 5 美元），不改也能直接下一步。
2. 中心节点在**本机屏幕**上显示二维码，内容是：relay 地址、这台设备专用的随机信箱编号和信箱口令、中心节点公钥、一次性配对密钥（256 位随机数，5 分钟过期，只能用一次）。**二维码不经过 relay 传送。**
3. 设备扫码，生成自己的密钥对，连到 relay 上的信箱，用 Noise IKpsk2 握手：配对密钥作为预共享密钥，证明这台设备确实扫过屏幕上的码。
   - **没有摄像头的设备**（另一台电脑、服务器）：控制台同时给出一串配对文字，在那台设备上运行 `omnillm connect pair <配对文字>`。配对文字要由主人自己搬过去（复制粘贴、SSH），不经过 relay。
   - **中心节点是没有屏幕的服务器**：二维码和配对文字显示在主人的 SSH 终端里，确认也在终端里完成。
4. **主人在中心节点上确认**：握手完成后，中心节点和设备屏幕上都显示同一个 6 位校验码（由握手结果算出）和设备名，主人核对一致后在中心节点上点确认。只偷拍到二维码的人配不上，因为确认要在中心节点前完成。
5. 中心节点记下设备公钥和权限，作废配对密钥。relay 全程只看到密文。

### 3.3 设备管理

- 每台设备单独设可用模型、日 / 月额度和到期时间。设备列表显示每台设备的名字、最近使用时间、本月花费（估算金额）。
- **管理设备**：主人可以把一台自己常带的设备（通常是手机）设为管理设备。在它上面经加密会话可以做“收紧”的操作：吊销别的设备、暂停全部、调低额度、查看用量。它不能新配对设备（必须在中心节点前完成），也不能放宽额度。丢了笔记本或别的手机时，用它马上吊销。管理设备上的这些操作需要先在本机解锁（系统生物识别）。
- `omnillm revoke <设备>` 立即生效：中心节点删除这台设备的公钥，并让 relay 关掉它的信箱。
- 每台设备一个独立信箱，信箱编号是随机数，和设备名、主人身份都没有关联。
- **relay 登记**：中心节点第一次连 relay 时，用 relay 部署者签发的登记令牌登记；只有登记过的中心节点能创建和关闭信箱，陌生人不能在 relay 上开信箱。
- **更换 relay**：中心节点经现有加密会话把新 relay 地址发给每台设备（由中心节点密钥签名），设备核对后切换，不用重新配对。
- **换电脑**：`omnillm backup` 导出一个用口令加密的备份（中心节点密钥、设备列表、额度设置、凭据），在新电脑上 `omnillm restore`。中心节点密钥没变，所有设备不用重新配对，下次连上就是新电脑。备份含凭据，导出时提醒妥善保管，恢复后旧电脑自动失效（同一时间只能有一个中心节点在线）。
- **中心节点丢了或被偷**：在管理设备上“暂停全部”，然后按控制台给出的清单到各提供商后台作废 API Key（OmniLLM 替不了这一步，清单会列出每个 Key 在哪个提供商、末 4 位），最后在新电脑上用备份恢复或重新开始。
- **设备之间不直接通信**：需要配合时（比如手机上的对话要调用另一台电脑上的 NEXA 工具），由中心节点在两条加密会话之间转接（§8.3）。

## 4. 核心技术

| 领域 | 选型 | 理由 |
|---|---|---|
| 语言 | **Go 1.25+** | 单文件、跨平台（macOS、Linux、Windows，amd64 和 arm64）、内存安全 |
| 端到端加密 | **Noise 协议**（`flynn/noise`）：IK / IKpsk2，X25519 + ChaCha20-Poly1305 + BLAKE2s | 成熟、被 WireGuard 等广泛采用的公钥握手框架，有前向保密，不自己发明协议 |
| 网页端加密 | X25519 用 WebCrypto（私钥不可导出）；ChaCha20-Poly1305 和 BLAKE2s 用 `@noble/ciphers` / `@noble/hashes`（经过审计） | WebCrypto 没有 ChaCha20，私钥又必须不可导出，所以密钥交换和对称加密分开实现；浏览器不支持 WebCrypto X25519 时拒绝使用，不退回可导出的私钥 |
| 中转传输 | WebSocket over TLS 1.3（`coder/websocket`）；relay 证书用 `x/crypto/acme/autocert` | 双方都主动外连，穿得过 NAT 和防火墙 |
| 上游出口 | `net/http` + 自写的限流、退避、熔断 | 封号防护集中在一处 |
| 存储 | SQLite（`modernc.org/sqlite`，纯 Go） | 单文件、免安装、免 CGO |
| 凭据存放 | `zalando/go-keyring`；无桌面环境时用 `filippo.io/age` 加密文件 | 用系统级保护，不自己造加密 |
| 本机控制台认证 | 本机登录用户身份：`omnillm open` 用只有当前用户可读的一次性令牌打开控制台 | 控制台只在本机，本机用户本来就登录过了，再设密码或 Passkey 只增加步骤 |
| 通知 | macOS / Windows 系统通知；手机用 Web Push，推送内容只有“有事需要处理”，不带任何细节 | 推送经过苹果、谷歌的推送服务，所以推送里不放内容 |
| 网页客户端 | TypeScript + Preact，从独立静态地址发布；Service Worker 锁定代码，只接受签名更新 | relay 不能下发代码，否则能偷钥匙（§5.3） |
| 二维码 | `skip2/go-qrcode`，终端显示 | 配对零输入，公钥当面交换 |
| 构建与发布 | GoReleaser + cosign 签名 + SBOM（syft）+ `govulncheck` | 发布物可校验，依赖漏洞进 CI |

## 5. 安全设计

### 5.1 威胁模型

| 资产 | 主要威胁 |
|---|---|
| 账号本身 | 多 IP、多设备并发、超限、绕过限制，被提供商封号 |
| API Key 和登录会话 | 中心节点被入侵、磁盘或备份泄露、日志泄露、被设备拿走 |
| 对话内容和元数据 | **中转服务器**偷看或篡改、中间人攻击、日志留存 |
| 设备私钥 | 手机丢失、恶意网页、被替换的网页客户端代码 |
| 本机接口 | 同一台机器上的其他程序、恶意网页经浏览器打本机端口（DNS 重绑定、跨站请求） |
| 额度和钱 | 设备被盗后盗刷 |

中转服务器按“诚实但好奇、也可能被攻破”的对手来设计：它拿到的东西泄露了，也不能危及内容和凭据。

### 5.2 防封号（原则 1）

- **单一出口**：所有上游请求只从中心节点的 Provider 出口发出；设备端没有任何直连提供商的代码，CI 扫描设备端构建产物，出现提供商域名即失败。
- **像一个人在用**：一个中心节点只服务一个主人；同一提供商默认最多 2 个并发；每分钟请求数和 token 数上限低于提供商公布的限额，并按上游返回的限流响应头动态收紧。
- **人优先**：并发名额先给人正在进行的对话，后台调用（标为 `Background` 的库调用和应用令牌）排在后面，NEXA 跑判断时手机上的对话不会卡住。
- **被限流就退**：429 和 `Retry-After` 严格遵守，指数退避；连续触发进入熔断，暂停该提供商一段时间并通知主人。不重试轰炸。
- **不规避**：不轮换账号、Key、IP，不伪造客户端标识。
- **出口稳定**：记录中心节点出口所在的国家或地区，变化时暂停上游请求，等主人确认；IP 变化只记录不暂停（笔记本换网络是正常的，按 IP 暂停会让 Mac 做中心时天天被卡住）。出口地区不在提供商支持的地区清单里时，不向该提供商发请求。
- **自动化调用分开**：后台调用（库调用标为 `Background`，如 NEXA 的判断；以及所有应用令牌）默认只能走官方 API Key 和本地模型；OAuth 登录得来的订阅额度只给人手动对话用，除非该提供商条款明确允许自动化调用。后台程序用订阅额度跑批量判断，是最容易被封的用法。
- **合规凭据**：只接入官方 API Key、提供商为第三方应用开放的 OAuth 登录和本地模型；不接网页版订阅的会话 Cookie。
- **额度兜底**：每台设备和全局都有额度上限；异常用量（一小时内超过日均的 5 倍）自动暂停该设备。

### 5.3 中转服务器看不到内容（原则 2）

- **端到端加密**：所有业务消息在设备和中心节点之间用 Noise 会话加密，relay 只转发密文。
- **防冒充**：中心节点公钥只能从屏幕上的二维码拿到，设备每次连接都校验；relay 换不了公钥，也就做不了中间人。配对时的预共享密钥同样只在二维码里。
- **不让 relay 下发代码**：`omnillm connect` 和原生 App 是签名的程序。网页客户端从独立的静态地址（如项目的 GitHub Pages）发布，首次安装后由 Service Worker 锁定，之后只接受用发布密钥签名的新版本，签名不对就继续用旧版本并提示。
  - 如实说明：浏览器不会校验第一次加载的页面，所以**首次安装那一刻要信任托管方**；“公开构建哈希”只能事后核对，挡不住第一次。对安全要求高的场景用 `omnillm connect` 或原生 App。
- **防重放**：握手第一条消息不带业务数据；会话内每条消息有递增编号，乱序或重复的直接丢弃并断开。
- **少留痕**：relay 不落盘、不记内容日志；消息按固定长度档位（如 1 / 4 / 16 / 64 KB）填充；信箱编号是随机数，和主人身份无关。
- **如实说明 relay 能看到的**：双方的 IP、连接时间、流量大小、流式回复的节奏（大致能推出回复长度）、哪些信箱在线。这些在 v1 不再进一步隐藏，文档和界面都不宣称“服务器什么都不知道”。
- **测试守住**：用一组哨兵明文跑完配对和对话，断言 relay 收到的每一帧、日志和内存快照里都找不到这组明文。

### 5.4 凭据保护：API Key 和登录会话（原则 3）

两类凭据同一套规则：**只在中心节点里存、在中心节点里用，不以任何形式发到别的设备。**

- **存放**：API Key、OAuth 的 access / refresh token 只存在系统钥匙串或 age 加密文件里，不进 SQLite、配置文件和日志；只有 Provider 出口能读，用完即弃。不接受任何网页会话 Cookie（§5.2）。
- **登录**：OAuth 授权码 + PKCE 或设备码流程由中心节点发起，回调地址是本机 `127.0.0.1`；只能在中心节点本机发起，设备无权发起登录，也无权读取、导出登录状态。
- **刷新**：token 只在中心节点刷新。刷新失败时，设备只收到“需要在中心节点重新登录”，不会收到任何 token 片段。
- **出口过滤**：返回设备的内容统一经过一个出口：只取上游的正文和必要字段，不转发上游响应头；上游原始报错改写成固定文案。
- **测试守住**：放一组哨兵凭据跑完全部功能，断言任何发往 relay 的明文（加密前）、日志、审计里都不出现哨兵值。
- **显示**：接口和管理页面永远不回显凭据，只显示末 4 位和到期时间；日志脱敏 `Authorization`、`Cookie`、`x-api-key`、`sk-*` 和 JWT 形态字符串。

### 5.5 网络暴露最小

- 中心节点**不监听任何对外端口**，只开 `127.0.0.1` 上的两个端口：本机控制台和本机应用接口。设备端 `omnillm connect` 也只监听 `127.0.0.1`。
- **本机端口也要设防**：同一台机器上的任何程序、以及浏览器里的恶意网页都能打到 `127.0.0.1`。所以：
  - 本机应用接口每个请求都要应用令牌；本机控制台要 `omnillm open` 给出的一次性令牌，换成只对本机有效的会话 Cookie（`HttpOnly; SameSite=Strict`）。
  - 校验 `Host` 头只认 `127.0.0.1` / `localhost`，防 DNS 重绑定。
  - 带 `Origin` 头的请求（来自浏览器）一律拒绝，控制台除外（控制台只认自己的来源）；不返回任何 CORS 允许头。
  - 多用户的服务器上，端口改用只有本用户能访问的 Unix 套接字。
- relay 只开 443，对未知信箱一律拒绝；连接和消息按 IP、信箱限流。

### 5.6 访问控制与防盗刷

- 设备身份就是它的公钥；吊销即删除公钥并关闭信箱。
- 每台设备有日、月额度上限，全局总额度封顶；超了直接拒绝。
- 配对密钥一次性、5 分钟过期，还要主人在中心节点上确认；配对失败多次即作废这个二维码。
- 应用令牌和设备一样，单独设模型、额度和并发，可单独吊销。
- 手机丢失时，最坏的损失是这台设备的额度：吊销即止。网页客户端和 App 可以开启本机解锁（系统生物识别），防止拿到手机的人直接用。

### 5.7 内容与隐私

- 默认不保存对话内容；审计只记元数据，而且只存在中心节点。
- 开启“保存历史”后，内容用中心节点主密钥加密再写库。
- 不接入任何遥测或第三方统计。

### 5.8 网页客户端安全

- 严格 CSP：`default-src 'self'`，`connect-src` 只允许配置的 relay 地址，不允许内联脚本和第三方资源。
- 私钥用 WebCrypto 不可导出保存；不放 URL、不放 localStorage。
- 加 `nosniff`、`no-referrer`、`frame-ancestors 'none'`。

### 5.9 供应链与发布

- 依赖尽量只用标准库和 `golang.org/x`；新增依赖要评审，CI 跑 `govulncheck` 和 `gosec`。
- 发布物用 cosign 签名并附 SBOM；安装脚本先校验签名再安装；网页客户端公开构建哈希。
- 自动更新只接受签名有效的版本，不允许降级。
- 仓库开启 Dependabot、secret scanning 和分支保护。

### 5.10 安全默认值一览

| 项 | 默认值 |
|---|---|
| 中心节点对外端口 | 无（只开本机管理端口） |
| 中心节点和设备的通信 | 只经 relay，端到端加密 |
| 上游并发 | 每个提供商 2 |
| 收到 429 | 按 `Retry-After` 退避，连续触发熔断 |
| 出口国家 / 地区变化 | 暂停上游请求，等主人确认（IP 变化只记录） |
| 应用令牌可用的凭据 | 只有官方 API Key 和本地模型 |
| 本机接口的浏览器请求 | 拒绝 |
| 配对密钥 | 5 分钟、一次性，中心节点上确认 |
| 登录会话 | 只在中心节点存和刷新，不可导出 |
| 对话内容存储 | 关闭 |
| 单设备、单应用日额度 | 默认每天 5 美元（估算），可改，不能设成无限 |
| 并发名额 | 人的对话优先，后台程序排后 |

### 5.11 可用性

- 中心节点离线（Mac 合盖睡眠、断网）时，所有设备都用不了；设备收到明确的“中心节点离线”（本机接口返回 503），不是超时或空结果。
- 要随时可用，就把中心节点放在常开的服务器或 NAS 上；Mac 做中心时，向导会问“要不要在接电源时保持唤醒”，默认勾选，主人可以改。
- 设备上随时能看到中心节点是否在线、最后在线时间；离线时提示具体原因和办法（如“你的 Mac 可能在睡眠，唤醒后会自动恢复”），恢复后自动重连，不用手动操作。
- relay 挂了同样全部不可用；relay 是无状态的，换一台或多部署一台都不用重新配对（§3.3）。

## 6. 接口（草案）

**设备本机**（`omnillm connect` 提供，只监听 `127.0.0.1`）

| 接口 | 说明 |
|---|---|
| `GET  /v1/models` | 当前设备可用的模型 |
| `POST /v1/chat/completions` | OpenAI 兼容，支持 `stream` |
| `POST /v1/messages` | Anthropic 兼容 |

**设备 ↔ 中心节点**（经 relay，Noise 加密后的消息）：`models.list`、`chat.start`、`chat.chunk`、`chat.cancel`、`usage.get`。

**relay**：`wss://<relay>/mailbox/<信箱编号>`，只认信箱口令，只转发字节。

**中心节点本机应用接口**（仅限 `127.0.0.1`，要应用令牌）：和设备本机接口相同的 `/v1/*`，给同一台机器上不能嵌入库的第三方程序用（NEXA 以库嵌入，不走这里）。

**中心节点本机控制台**（仅限 `127.0.0.1`，凭 `omnillm open` 的一次性令牌）：`/console/*`，向导、设备、应用令牌、额度、Provider、登录、用量、审计。

`GET /v1/models` 的每个模型带 `x_omnillm` 字段：`locality`（`local` 表示数据不出这台机器，`remote` 表示会到云端）和 `provider`。调用方按它如实显示数据去向（嵌入库的宿主直接读 `Model.Locality`）；字段缺失时一律按 `remote` 处理。

本机接口的错误状态码（固定，调用方可以据此分支）：

| 状态码 | 含义 | 正文 `error.code` |
|---|---|---|
| 400 | 请求本身不被支持，如这个模型不支持所给的 `response_format` | `unsupported_response_format` 等 |
| 401 | 令牌缺失、无效或已吊销 | `invalid_token` |
| 403 | 令牌有效，但不允许用这个模型（不在这枚令牌的模型清单里，或该模型只能人手动使用） | `model_not_allowed` |
| 429 | 排队已满或上游限流，带 `Retry-After` | `busy` |
| 503 | 中心节点离线或连接服务不通 | `hub_offline` |

`error.message` 是给人看的一句话（中英按 `Accept-Language`），不含凭据和上游原始报错。

模型名用 `provider/model` 形式（如 `anthropic/claude-sonnet-5-5`、`ollama/qwen3`），也支持别名。界面上显示人看得懂的名字（如“Claude Sonnet 5.5”“本地 Qwen3”），并有一个默认模型，日常对话不用每次选。

## 8. 融入 NEXA（以 SDK 嵌入，不另装软件）

NEXA（`pgclient`，Go）直接引入 OmniLLM 库。用户只装 NEXA：在 NEXA 里打开“在其他设备上用”，就能把手机配对上来；NEXA 自己的判断模型也可以选 OmniLLM 管理的模型。

### 8.1 NEXA 里的两种角色

| 情况 | NEXA 嵌入 | 用户在 NEXA 里看到 |
|---|---|---|
| NEXA 所在的电脑就是主机（最常见） | `hub` | “这台电脑是主机”：接入模型、添加设备、设备列表、用量，都在 NEXA 自己的页面里 |
| 主机在别处（例如家里的 NAS 上另有一个 NEXA 或 `omnillm` 独立程序） | `device` | “连到我的主机”：扫码或粘贴配对文字，之后 NEXA 用主机上的模型 |

一个主人只有一个主机。NEXA 设置里二选一，默认“这台电脑是主机”。

### 8.2 角色一：当 NEXA 的大模型（判断模型）

- **怎么接**：NEXA 的 `omnillm` 提供方直接调用库：主机角色调 `hub.Complete`，设备角色调 `device.Complete`。不走本机 HTTP，不需要应用令牌，也不用写任何 Key 或地址到 NEXA 的配置里。
- **调用方标为后台**：NEXA 的判断是后台自动调用，每个请求都标 `Background`：只能走官方 API Key 和本地模型，不用订阅额度（§5.2）；并发名额排在人的对话后面。
- **数据去向**：NEXA 直接读 `Model.Locality`。主机角色下，本地模型（如 Ollama）是“只在本机”，云端模型是“到某某提供商”；设备角色下，所有模型都是“经主机到……”，不算本机。
- **出站走 NEXA 的出口**：库发往提供商的请求经 NEXA 传入的传输层，NEXA 的出站记录（数据去向图）里能看到每一次调用去了哪家。
- **结构化输出**：`Request` 里带 JSON Schema；模型支持就用上游的结构化输出，不支持返回 `ErrUnsupportedFormat`，NEXA 降级，不假装支持。
- **错误**：`ErrBusy`（带 `RetryAfter`）、`ErrHubOffline` 是“忙或不可用”，不能当结论（NEXA 原则 37）；`ErrModelNotAllowed` 有自己的提示语。
- **NEXA 已有的分支**（pgclient `claude/frosty-ptolemy-5ddb87`，按本机 HTTP 接口实现）里的数据去向规则、错误映射和提示语可以保留，调用方式要改成库调用（§8.4）。

### 8.3 角色二：当 NEXA 的 AI 应用

在手机上和模型对话时，模型可以调用 NEXA 的工具（查待处理事项、看今天的进展、找人等）。

- **谁在哪一步**（按原则 1、2）：
  1. 对话的模型循环在主机上跑，因为只有主机能调模型。
  2. 模型要调用 NEXA 工具时，由嵌在 NEXA 里的库执行：主机角色下就在本进程；设备角色下，主机把调用经加密会话发给那台 NEXA，再把结果加密送回。
  3. 手机只和主机说话，和 NEXA 那台电脑之间没有直连。
- **工具怎么登记**：NEXA 把自己的 MCP 工具分发器包成 `ToolHost` 传给库，每个工具带名字、参数结构、是否只读。库调用工具时走 NEXA 的这个分发器，所以 NEXA 的规则一条不少：结果里标了 `untrusted` 的内容当数据显示；被拦截的显示“已拦截”；对外动作照常弹 NEXA 自己的确认框，库不能自动确认，也不能绕过。
- **工具白名单**：在 NEXA 里勾选哪些工具可以从别的设备调用，默认只读类；不在白名单里的直接拒绝。主机被攻破时，攻击者也只能调白名单里的工具，对外动作仍要过 NEXA 的确认框。
- **不再需要** `pgclient agent setup` 登记、`omnillm ask` 命令和 stdio 方式的 `pgclient mcp`：这些是给外部程序用的，嵌入后都在进程内完成。

### 8.4 NEXA 侧需要做的事

| 事项 | 说明 |
|---|---|
| 引入 OmniLLM 库 | `go get github.com/wensuper/OmniLLM`；库的 `go` 版本要求不高于 NEXA 的 Go 1.27.2，依赖和 NEXA 现有的重合 |
| 实现宿主接口 | 钥匙串、存储、出站出口（`internal/egress`）、日志、语言、确认框和通知、工具分发 |
| `omnillm` 提供方改成库调用 | 保留已有分支里的数据去向规则、错误映射和中英提示语，把本机 HTTP 调用换成 `hub.Complete` / `device.Complete`，数据去向改读 `Model.Locality` |
| NEXA 页面加“在其他设备上用” | 主机 / 设备二选一、接入模型、添加设备（二维码、配对文字、6 位校验码）、设备列表、用量；中英双语、深浅色、375 px |
| 工具白名单设置 | 在 NEXA 里勾选可从别的设备调用的工具 |

这些改动在 NEXA 仓库按它自己的流程做和发版。OmniLLM 这边先把库的公开接口做稳（v0.1），NEXA 再接入。

## 9. 已定决策

1. **许可证**：Apache-2.0（2026-10-18）。
2. **只有中心节点和大模型交互，严防封号**：原则 1（2026-10-18）。
3. **中心节点和设备只经服务器中转，端到端非对称加密，服务器看不到内容**：原则 2（2026-10-18）。因此撤销 v0.1 里“推荐 Tailscale”和“局域网直连”的决定。
4. **客户端**：先做 `omnillm connect` 和网页客户端；网页客户端不由 relay 下发。原生 App 等需求明确后再做。
5. **融入 NEXA**：以 SDK 嵌入 NEXA，不另装软件；当 NEXA 的大模型和 AI 应用，原则 7（2026-10-18 改定，原先的“本机 HTTP + 应用令牌 + `agent setup` 登记”方式只留给第三方程序）。
6. **架构评审修正**（2026-10-18，见 §11）。
7. **产品评审修正**（2026-10-18，见 §12）：默认公共 relay、首次运行向导、本机控制台不设密码、管理设备、备份迁移、一步接入 NEXA。

## 10. 用户体验与易用性

### 10.1 第一次使用（目标 5 分钟）

1. **安装**：Mac 上 `brew install omnillm` 或下载安装包；Linux 一行安装脚本（先校验签名）。安装完自动打开本机控制台。
2. **向导第 1 步：接入模型**。三个选项并排：
   - 粘贴 API Key：自动识别是哪家，当场发一个最小请求验证，成功才保存；失败时说清是 Key 错了、没开通余额，还是地区不支持。
   - 用本地模型：检测到本机的 Ollama 就直接列出已下载的模型，一键接入。
   - 只有网页订阅？说明为什么用不了，给出申请 API Key 和安装 Ollama 的链接。
3. **向导第 2 步：配对手机**。显示二维码；手机相机扫码打开网页客户端，按提示“添加到主屏幕”；两边核对 6 位校验码，在电脑上点确认。额度已预填。
4. **向导第 3 步：试一下**。手机上已经选好默认模型，输入框里预填一句“你好”，发出去看到回复，向导完成。
5. Mac 上向导最后问一句：“要让手机随时能用，接电源时保持唤醒吗？”默认勾选。

整个过程不需要服务器、不需要改路由器、不需要命令行。

### 10.2 用户看到的说法

界面上只用下面这些词，不出现 relay、Noise、信箱、令牌哈希等内部名词。

| 内部名词 | 界面上的说法 |
|---|---|
| 中心节点（hub） | 主机（如“你的 MacBook”） |
| 设备 | 设备 |
| 中转服务器（relay） | 连接服务（只在设置里出现，“使用公共连接服务 / 使用自己的”） |
| 应用令牌 | 已接入的应用（如某个 App） |
| 配对密钥、校验码 | 二维码、“核对两边的数字是否一致” |
| token 用量 | 花费（估算），token 数放在详情里 |

### 10.3 日常使用

- **手机上**：打开主屏幕上的图标就是对话；顶部一个小圆点显示主机在线与否。换模型在输入框旁边一个下拉框里，显示人看得懂的名字。
- **电脑或服务器上的 App**：`omnillm connect` 装好后开机自启，App 里把地址填成它给的 `http://127.0.0.1:<端口>/v1` 即可；控制台里有常见 App 的填写示例。
- **用量**：控制台首页是本月花费（估算，按提供商公布价格计算并标明“估算”）、每台设备和每个应用的花费、离额度还剩多少。
- **快到额度**：用到 80% 时提醒一次；用完时对话里直接说明“今天的额度用完了，明天恢复，或在主机上调高”，不是报错代码。

### 10.4 出问题时

每条提示都说：发生了什么、为什么、下一步。示例：

| 情况 | 提示 |
|---|---|
| 主机离线 | 你的 MacBook 现在连不上，可能在睡眠或断网。唤醒后会自动恢复。 |
| 主机因地区变化暂停 | 主机所在地区变了（中国香港 → 日本），为防止账号被判异常，已暂停调用。请在主机或管理设备上确认继续。 |
| 提供商限流 | Anthropic 让我们稍等，大约 30 秒后自动重试。 |
| API Key 失效 | Anthropic 的 Key（末 4 位 a1b2）已失效，请在主机控制台更换。 |
| 设备被吊销 | 这台设备已被移除。如需继续使用，请在主机上重新添加。 |
| 网页客户端更新签名不对 | 收到的新版本没有通过校验，继续使用当前版本。如果反复出现，请告诉我们。 |

### 10.5 丢东西和换东西

| 情况 | 怎么办 |
|---|---|
| 丢了手机 | 在主机控制台或另一台管理设备上点“移除”，立即生效；最坏损失是这台手机当天的额度 |
| 换手机 | 新手机扫码添加，旧手机移除 |
| 换电脑（主机） | 旧电脑 `omnillm backup` → 新电脑 `omnillm restore`，所有设备不用重新添加 |
| 主机丢了或被偷 | 管理设备上“暂停全部”，按清单到各提供商后台作废 Key，再用备份恢复或重新开始 |

### 10.6 语言和无障碍

- 控制台、网页客户端、命令行提示都中英双语，跟随系统语言，可以切换。
- 网页客户端支持深浅色、375 px 窄屏、系统字号放大和读屏。

## 11. 架构评审修正（2026-10-18）

| # | 问题 | 修正 |
|---|---|---|
| 1 | 按出口 IP 突变暂停：Mac 做中心时一换网络就停，等于不能用 | 改为按国家或地区变化暂停，IP 变化只记录；加上“出口地区不在提供商支持清单就不发请求” |
| 2 | NEXA 这类后台程序用订阅额度自动化调用，是最容易被封的用法，原设计没区分 | 应用令牌默认只能走官方 API Key 和本地模型 |
| 3 | Noise IK 第一条消息可被重放，若带业务数据会重复触发请求 | 不做 0-RTT；会话内消息编号递增，乱序或重复即断开 |
| 4 | 二维码被偷拍就能在 5 分钟内配上 | 配对最后一步由主人在中心节点上核对 6 位校验码并确认 |
| 5 | “网页客户端公开构建哈希”挡不住首次加载被替换 | Service Worker 锁定代码、只接受签名更新；如实写明首次安装要信任托管方，高要求场景用 connect 或 App |
| 6 | 网页端用 noble 做 X25519 就要拿到私钥原文，和“私钥不可导出”矛盾 | X25519 用 WebCrypto（不可导出），对称加密用 noble；不支持就拒绝 |
| 7 | 本机 127.0.0.1 端口会被同机程序和浏览器恶意网页打到 | 本机接口必须令牌；校验 Host；拒绝带 Origin 的浏览器请求；多用户服务器改 Unix 套接字 |
| 8 | 当 NEXA 的 AI 应用时，模型循环、工具执行分别在哪不清楚，可能变成设备之间直连 | 模型循环在中心节点，工具在 NEXA 那台机器执行，由中心节点转接；远程可调的工具有白名单 |
| 9 | 原则 2 没说同一台机器上的程序算不算“设备” | 写明同机程序走本机接口、不经 relay，凭应用令牌访问 |
| 10 | 凭据里列了“会话 Cookie”，又说不接网页订阅 Cookie，自相矛盾 | 凭据只有 API Key 和 OAuth token，不接受任何网页会话 Cookie |
| 11 | relay 谁都能开信箱；换 relay 要重新配对；没有协议版本和换钥方案 | 中心节点凭登记令牌才能开信箱；新 relay 地址和新公钥经加密会话签名下发；握手带协议版本，只增不改 |
| 12 | 没写中心节点离线时的表现 | 加 §5.11：离线明确返回 503；常开场景放服务器；Mac 接电源时可阻止睡眠 |
| 13 | `/v1/models` 的数据去向字段没有定义，NEXA 无法实现 | 定义 `x_omnillm.locality` / `provider`，缺失按 `remote` |

## 12. 产品评审修正（2026-10-18）

| # | 问题 | 修正 |
|---|---|---|
| 1 | 要用户自己有一台公网服务器跑 relay，绝大多数人卡在第一步 | 默认用项目提供的公共 relay，什么都不用装；自己部署变成可选 |
| 2 | 没有首次使用流程，只有一堆命令 | 加首次运行向导：接入模型 → 配对手机 → 发第一条消息，目标 5 分钟（§10.1） |
| 3 | 只有网页订阅、没有 API Key 的人装完才发现用不了 | 在“谁能用”、安装说明和向导第一步就说清，并给出替代办法 |
| 4 | 本机控制台要设 Passkey，人已经登录在这台电脑上，多一步还容易卡住 | 本机控制台凭本机登录用户身份进入，去掉 Passkey |
| 5 | 管理只能在主机上做，人在外面丢了手机没法处理 | 加“管理设备”：在常带的手机上能吊销、暂停、调低额度，只能收紧不能放宽 |
| 6 | “单设备额度必须设置”等于每次配对都多一道填空题 | 额度预填每天 5 美元，可改，不能设成无限 |
| 7 | 另一台电脑、服务器没有摄像头，扫不了码；无屏幕服务器做主机没法显示二维码 | 加配对文字（主人自己复制过去）；无屏幕主机在 SSH 终端里显示和确认 |
| 8 | 换电脑要所有设备重新配对；主机丢了不知道怎么办 | 加加密备份和恢复，设备不用重新配对；加“主机丢了”清单 |
| 9 | 接入 NEXA 要手动发令牌、复制、改配置三步 | 已被 v0.5 取代：OmniLLM 以库嵌入 NEXA，用户不用接入任何东西（§8） |
| 10 | NEXA 后台判断会占满并发，手机上对话卡住 | 并发名额人优先，后台程序排后 |
| 11 | 用量只有 token 数，普通人看不懂 | 用量以估算金额为主，token 数放详情；用到 80% 提醒 |
| 12 | 错误提示没有设计，容易出现“503”“handshake failed” | 每条提示都写发生了什么、为什么、下一步（§10.4 示例） |
| 13 | 界面上会出现 relay、hub、令牌等内部名词 | 定了界面用语表（§10.2） |
| 14 | 主机离线时手机上不知道为什么、要不要做什么 | 手机上显示主机在线状态和最后在线时间，离线给原因和办法，恢复后自动重连；Mac 向导默认开“接电源时保持唤醒” |
| 15 | 模型名是 `anthropic/claude-sonnet-5-5` 这种，日常每次都要选 | 显示人看得懂的名字，并设默认模型 |
| 16 | 流式回复每一小块都填充到 1 KB，手机流量浪费 | 每约 100 毫秒合并成一块再加密发送 |
| 17 | 一行安装排在 v0.4，v0.1 等于没法给普通人用 | 安装、控制台、向导、公共 relay 都提到 v0.1 |
| 18 | 通知怎么到手机没设计，直接推送会把内容交给苹果、谷歌 | 手机用 Web Push，推送里只有“有事需要处理”，不带细节 |
| 19 | 没提语言和无障碍 | 中英双语、深浅色、窄屏、字号放大和读屏 |
